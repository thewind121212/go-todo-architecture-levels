# Level 6: Hexagonal (Ports & Adapters)

## 1. What this level teaches

The app is a hexagon. The domain and the service sit in the middle and talk to the outside only
through **ports** (interfaces). **Driving** adapters (HTTP) call into the app through the driving port
`ports.TodoService`. The app calls out through the **driven** ports (`TodoRepository`,
`ActivityRepository`, `TxManager`), and the Postgres and Mongo adapters implement them. The code is
sliced by feature (`internal/todo/...`) in the style of
[go-scaffolding](https://github.com/cuongtranba/go-scaffolding). This level also brings in the first
heavier tools: Wire, mockery and SQL migrations.

```
     DRIVING side                       THE HEXAGON                          DRIVEN side
   (calls the app)               domain + service + ports                (called by the app)

                               ______________________________
                              /                              \
 +-----------------+         /   ports.TodoService            \
 | adapters/http   | ------>|      (driving port)              |        +-------------------+
 | Gin handlers,   |        |             |                    |   +--->| adapters/postgres |
 | DTOs            |        |             v                    |   |    | GORM + migrations |
 +-----------------+        |    service.TodoService           |   |    +-------------------+
                            |    domain.Todo, domain.Activity  |---+          - or -
                            |             |                    |   |    +-------------------+
                            |             v                    |   +--->| adapters/mongo    |
                             \   ports.TodoRepository         /         | driver v2 + BSON  |
                              \  ports.ActivityRepository    /          +-------------------+
                               \ ports.TxManager  (driven)  /
                                \__________________________/

       Dependencies point inward: every adapter imports ports + domain, never the reverse.
       Wire plugs exactly one driven adapter set into the ports at startup.
```

## 3. Request flow: `PATCH /todos/:id`

1. **Startup**: `cmd/api/main.go` `newServer` sees `DB_DRIVER=postgres` and calls `initPostgresServer`
   in `wire_gen.go`. That function builds the repositories, the service and the router.
2. `internal/todo/adapters/http/routes.go` routes `PATCH /todos/:id` to `handler.update`.
3. `adapters/http/handlers.go` `update` binds the body into `updateTodoRequest` (`dto.go`). It
   builds a `ports.UpdateTodoInput` and calls `h.svc.Update`. The handler only knows the driving port.
4. `internal/todo/service/todo_service.go` `Update` rejects an empty update (`ErrEmptyUpdate`) and a
   malformed id (`ErrNotFound`). It then opens a transaction with `s.tx.WithinTx`.
5. `adapters/postgres/tx.go` starts a GORM transaction and puts it into the ctx. In Mongo,
   `adapters/mongo/tx.go` starts a session transaction instead.
6. Inside the transaction:
   * `s.todos.Get` runs `adapters/postgres/todo_repository.go`. It picks up the transaction with
     `conn(ctx)`, and `mappers.go` turns the `todoModel` into a `domain.Todo`.
   * `applyUpdate` calls `domain/todo.go` `Rename` and `SetCompleted`. These report what actually
     changed, which gives the actions `renamed`, then `completed` or `reopened`.
   * `s.todos.Update` writes the row. `s.record` creates a `domain.NewActivity` for each action and
     passes it to `activity_repository.go` `Append`.
7. If `fn` returns nil, GORM commits. If it returns an error, GORM rolls back.
8. Back in `handlers.go`, the handler sends `toTodoResponse` with status 200. Any error goes to
   `writeError` instead, which maps it to 400, 404 or 500.

## 4. Where the transaction lives

The **service** draws the boundary through the `ports.TxManager` driven port. It never sees a
`*gorm.DB` or a Mongo session (`internal/todo/service/todo_service.go`):

```go
err := s.tx.WithinTx(ctx, func(ctx context.Context) error {
	todo, err = s.todos.Get(ctx, id)
	...
	if err := s.todos.Update(ctx, todo); err != nil {
		return err
	}
	for _, action := range actions {
		if err := s.record(ctx, todo.ID, action); err != nil {
			return err // rolls back the todo update too
		}
	}
	return nil
})
```

Each driven adapter keeps the transaction in the ctx in its own way. Postgres
(`adapters/postgres/tx.go`):

```go
func (m *TxManager) WithinTx(ctx context.Context, fn func(ctx context.Context) error) error {
	return m.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		return fn(context.WithValue(ctx, txKey{}, tx))
	})
}

func conn(ctx context.Context, db *gorm.DB) *gorm.DB { // used by every repository call
	if tx, ok := ctx.Value(txKey{}).(*gorm.DB); ok {
		return tx
	}
	return db.WithContext(ctx)
}
```

Mongo (`adapters/mongo/tx.go`) needs no ctx key. The driver already puts the session into the ctx that
it passes to the callback:

```go
_, err = session.WithTransaction(ctx, func(ctx context.Context) (any, error) {
	return nil, fn(ctx)
})
```

## 5. What changed from level 5

Level 5 was **layer-first** Clean Architecture: `entity / usecase / adapter / infrastructure`, one use
case per struct, a hand-written composition root and hand-written fakes. Level 6 changes how the code
is organised and named, and adds three tools:

* **Sliced by feature, not by layer.** Everything about todos lives under `internal/todo/`: domain,
  ports, service and adapters. Only shared technical code (DB connections, health, logger, config)
  lives outside it. To add a feature, you add a sibling folder, not a file in each of four layers.
  Activities belong to the todo feature, so they live in `todo/domain` and `todo/ports`.
* **Ports are named explicitly.** The interfaces get their own `ports` package with a clear split.
  `service.go` holds the driving port. `repository.go` holds the driven ports. The L5 use-case structs
  become one service that implements the `TodoService` driving port, so a driving adapter depends on
  one interface, and a CLI or gRPC adapter could reuse it unchanged.
* **Wire** (`google/wire`) replaces the hand-written composition root. *Why now:* the graph now comes
  in two complete variants (Postgres and Mongo), each with a DB handle, three adapters, three
  interface bindings, a health check, a service, a router and a server. Wire checks the whole graph
  at generate time: a missing provider or an unbound port fails `go tool wire`, not startup. Its output
  (`wire_gen.go`) is plain Go you can read. *Why not earlier:* with five constructors, a manual `main`
  is shorter and clearer than a code generator.
* **mockery v3** replaces hand fakes. *Why now:* the ports are now the formal contract, with four
  interfaces and fourteen methods. Hand fakes would repeat all of them and drift. The mocks also check
  *interactions*: `WithinTx` was called, the repositories got the transaction's ctx (see `inTx` in
  `todo_service_test.go`), and nothing unexpected was called. *Why not earlier:* a ten-line fake
  teaches what a test double is. A generated mock hides that.
* **SQL migrations** (golang-migrate, embedded with `embed.FS`, run at startup) replace
  `AutoMigrate`. *Why now:* once persistence models are kept apart from the domain, the schema should
  be its own reviewed, versioned, reversible artifact, not a side effect of GORM struct tags.
  `AutoMigrate` cannot drop or rename columns and keeps no history. Mongo's equivalent is
  `database/mongo.go`, which creates the collections and the index. *Why not earlier:* for a two-table
  learning schema, `AutoMigrate` meant zero ceremony.

### Wire and the runtime DB choice

Wire resolves the graph at **compile time**, but `DB_DRIVER` is only known at **runtime**. The
solution is **one injector per storage choice** (`cmd/api/wire.go`):

```go
func initPostgresServer(ctx context.Context, cfg config.Config, log zerolog.Logger) (*http.Server, func(), error) {
	wire.Build(providers.PostgresSet)
	return nil, nil, nil
}
func initMongoServer(...) (*http.Server, func(), error) { wire.Build(providers.MongoSet); ... }
```

`main.go` `newServer` switches on `cfg.DBDriver` and calls the matching injector. An unknown value
fails fast with a clear message. The two sets in `internal/wire/providers.go` share `appSet` and
differ only in which adapter each `wire.Bind` plugs into each driven port:

```go
wire.Bind(new(ports.TodoRepository), new(*pgadapter.TodoRepository)),
```

I picked this over a single provider that switches on the driver and returns the port interfaces. A
switch like that would hide the binding in hand-written code. With two injectors, Wire still checks
every edge of both graphs.

## 6. Pros / cons / when to use this in real life

**Pros**
* The core has no idea Gin, GORM or Mongo exist. Swapping or adding an adapter (gRPC, a queue
  consumer, another database) touches no domain or service code.
* Feature slices scale: each feature folder is self-contained and easy to find, review and delete.
* Explicit driving/driven ports make the test strategy obvious. Mock the driving port to test
  adapters. Mock the driven ports to test the service. Run one contract suite to test the driven
  adapters for real.
* Wire, generated mocks and migrations take boilerplate off your hands and fail early (generate time
  or compile time).

**Cons**
* More packages, interfaces and mapping code than the app's size needs (models and DTOs mirror the
  domain three times).
* Three generators add steps. You must rerun `wire` and `mockery` after changing constructors or
  ports, and keep the generated files committed.
* Mock-based tests can couple to call order and arguments. Keep them focused on behavior that matters,
  like transactions and activities.

**When to use it:** services you expect to live for years, with more than one way in (HTTP plus
workers, gRPC or a CLI) or more than one way out, maintained by a team. For a small CRUD tool, level 3
or 4 is enough.

## 7. Run & test

```sh
export PATH=$HOME/.local/go/bin:$HOME/go/bin:$PATH
# from repo root, once: docker compose up -d

task run:pg                      # DB_DRIVER=postgres go run ./cmd/api  (migrates at startup), :8086
task run:mongo                   # DB_DRIVER=mongo    go run ./cmd/api

task test                        # go test ./...                    unit tests, no Docker
task test:integration            # go test -tags=integration ./...  testcontainers, both adapters + rollback
task lint                        # gofmt -l, go vet (with and without the integration tag)

task wire:generate               # go tool wire ./cmd/api
task mock:generate               # go tool mockery
task migrate:up                  # optional: golang-migrate CLI against todo_l06
task migrate:down                # optional: roll back the last migration

# smoke test (app running on :8086, from repo root)
python3 scripts/smoke.py http://localhost:8086
```
