# Level 6: Hexagonal (Ports & Adapters)

## What this level teaches

The app is a hexagon. The domain and the service sit in the middle and talk to the outside only
through **ports** (interfaces). **Driving** adapters (HTTP) call into the app through the driving port
`ports.TodoService`. The app calls out through the **driven** ports (`TodoRepository`,
`ActivityRepository`, `TxManager`), and the Postgres and Mongo adapters implement them. The code is
sliced by feature (`internal/todo/...`) in the style of
[go-scaffolding](https://github.com/cuongtranba/go-scaffolding). This level also brings in the first
heavier tools: Wire, mockery and SQL migrations.

```
     DRIVING side                       THE HEXAGON                          DRIVEN side
   (calls the app)               domain + service + ports                (called by the app)

                               ______________________________
                              /                              \
 +-----------------+         /   ports.TodoService            \
 | adapters/http   | ------>|      (driving port)              |        +-------------------+
 | Gin handlers,   |        |             |                    |   +--->| adapters/postgres |
 | DTOs            |        |             v                    |   |    | GORM + migrations |
 +-----------------+        |    service.TodoService           |   |    +-------------------+
                            |    domain.Todo, domain.Activity  |---+          - or -
                            |             |                    |   |    +-------------------+
                            |             v                    |   +--->| adapters/mongo    |
                             \   ports.TodoRepository         /         | driver v2 + BSON  |
                              \  ports.ActivityRepository    /          +-------------------+
                               \ ports.TxManager  (driven)  /
                                \__________________________/

       Dependencies point inward: every adapter imports ports + domain, never the reverse
       (arch_test.go enforces it). Wire plugs exactly one driven adapter set in at startup.
```

## Request flow: `PATCH /todos/:id`

1. **Startup**: `cmd/api/main.go` `newRouter` sees `DB_DRIVER=postgres` and calls `initPostgresApp`
   in `wire_gen.go`. That function builds the repositories, the service and the router.
2. `internal/todo/adapters/http/routes.go` routes `PATCH /todos/:id` to `handler.update`.
3. `adapters/http/handlers.go` `update` runs `todoID`, which calls `uuid.Parse`. A malformed id
   becomes `ErrNotFound`, and the service never sees it. The handler then binds the body into
   `updateTodoRequest` (`dto.go`) and calls `h.svc.Update` with a `ports.UpdateTodoInput`. The
   handler only knows the driving port.
4. `internal/todo/service/todo_service.go` `Update` checks the input before touching the database.
   An empty patch is `ErrEmptyPatch`, and a bad title fails `domain.ValidateTitle`. Both become 400,
   even for an unknown id. The service then takes one `now := nowUTC()` and calls `s.tx.WithinTx`.
5. `adapters/postgres/tx.go` starts a GORM transaction and puts it into the ctx. In Mongo,
   `adapters/mongo/tx.go` starts a session transaction instead.
6. Inside the transaction, only the diff happens:
   * `s.todos.GetForUpdate` runs in `adapters/postgres/todo_repository.go`. It picks up the
     transaction with `conn(ctx)` and runs `SELECT … FOR UPDATE`. `mappers.go` turns the row into a
     `*domain.Todo`, with times converted to UTC.
   * `applyChanges` calls `domain/todo.go` `Rename(title, now)` and `SetCompleted(completed, now)`.
     These return what actually changed: `renamed`, then `completed` or `reopened`.
   * `s.todos.Update` writes the row. Then `s.activities.Create` stores one
     `domain.NewActivity(id, action, now)` per change, through `activity_repository.go`.
7. If `fn` returns nil, GORM commits. If it returns an error, GORM rolls back.
8. Back in `handlers.go`, the handler sends `toTodoResponse` with status 200. Any error goes to
   `writeError` in `errors.go`, which maps it to 400, 404 or 500.

## Where the transaction lives

The **service** draws the boundary through the `ports.TxManager` driven port. It never sees a
`*gorm.DB` or a Mongo session (`internal/todo/service/todo_service.go`):

```go
now := nowUTC()
err := s.tx.WithinTx(ctx, func(ctx context.Context) error {
	todo, err = s.todos.GetForUpdate(ctx, in.ID)
	...
	if err := s.todos.Update(ctx, todo); err != nil {
		return err
	}
	for _, action := range actions {
		if err := s.activities.Create(ctx, domain.NewActivity(todo.ID, action, now)); err != nil {
			return err // rolls back the todo update too
		}
	}
	return nil
})
```

Each driven adapter keeps the transaction in the ctx in its own way. Postgres
(`adapters/postgres/tx.go`):

```go
func (m *TxManager) WithinTx(ctx context.Context, fn func(ctx context.Context) error) error {
	return m.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		return fn(context.WithValue(ctx, txKey{}, tx))
	})
}

func conn(ctx context.Context, db *gorm.DB) *gorm.DB { // used by every repository call
	if tx, ok := ctx.Value(txKey{}).(*gorm.DB); ok {
		return tx
	}
	return db.WithContext(ctx)
}
```

Mongo (`adapters/mongo/tx.go`) needs no ctx key. The driver already puts the session into the ctx that
it passes to the callback. Its `GetForUpdate` is a plain find: a concurrent writer causes a write
conflict, and `WithTransaction` retries.

```go
_, err = session.WithTransaction(ctx, func(ctx context.Context) (any, error) {
	return nil, fn(ctx)
})
```

## What changed from the previous level

Level 5 was **layer-first** Clean Architecture. Level 6 slices **by feature** and names the ports:

```
level-05-clean/internal/                 level-06-hexagonal/internal/
  entity/        todo, activity, errors    todo/domain/              todo, activity, errors
  usecase/ports.go  repos + TxManager      todo/ports/repository.go  driven ports (same three)
  (input ports in adapter/http)            todo/ports/service.go     driving port TodoService
  usecase/create_todo.go, get_todo.go,     todo/service/todo_service.go   one service, six methods
    list_todos.go, update_todo.go,
    delete_todo.go, list_activities.go
  usecase/output.go  TodoOutput, ...       (gone: the port returns *domain.Todo)
  (hand fakes in usecase/fakes_test.go)    todo/ports/mocks/         generated by mockery
  adapter/http/  controllers, presenter    todo/adapters/http/       handler, dto, routes, errors
  adapter/postgres/ db.go AutoMigrate      todo/adapters/postgres/   repos only; schema is in migrations/
  adapter/mongo/    db.go                  todo/adapters/mongo/      repos only
  infrastructure/config/                   config/                   (go-scaffolding layout)
  infrastructure/server/                   infrastructure/server/    unchanged
                                           infrastructure/database/  connect + migrate (was adapter/*/db.go)
                                           infrastructure/health/    + /health/live, /health/ready
                                           infrastructure/logger/
  cmd/api/main.go  manual composition      cmd/api/wire.go + wire_gen.go   Wire; main picks the injector
                                           wire/providers.go         provider sets
                                           ../migrations/            versioned SQL
```

Some names stay the same: `NewTodo`, `Rename`, `SetCompleted`, `NewActivity`, `ValidateTitle`,
`nowUTC`, `UpdateTodoInput`, `applyChanges`, `GetForUpdate`, `ListByTodo`, `WithinTx`, `writeError`,
`todoID`, `parsePage` and the sentinel errors. Others change because of the architecture:

* **Use-case structs → one service.** The six `Execute` interactors become six methods on
  `service.TodoService`, behind one driving port. Any driving adapter (HTTP today, gRPC or a CLI later)
  depends on that one interface, and mockery can mock it.
* **No output DTOs.** The driving port returns `*domain.Todo` and `*domain.Activity`, as
  go-scaffolding does. The HTTP adapter maps them to its own DTOs. Entities are pointers here,
  mirroring go-scaffolding. Level 5 used values, and the behavior is the same.
* **Controllers → one `handler`**, because there is one driving port to call.
* **The DB connection moves out of the adapters** into `infrastructure/database`, because the schema
  is no longer a GORM side effect. The adapters keep only models, mappers and repositories.

Three tools appear, each because the hexagon now needs it:

* **Wire** (`google/wire`) replaces the hand-written composition root. *Why now:* the graph now comes
  in two complete variants (Postgres and Mongo), each with a DB handle, three adapters, three port
  bindings, a health check, a service and a router. Wire checks the whole graph at generate time: a
  missing provider or an unbound port fails `go tool wire`, not startup. Its output (`wire_gen.go`) is
  plain Go you can read. *Why not earlier:* with a handful of constructors, a manual `main` is shorter
  and clearer than a code generator.
* **mockery v3** replaces hand fakes. *Why now:* the ports are now the formal contract, with four
  interfaces and fifteen methods. Hand fakes would repeat all of them and drift. The mocks also check
  *interactions*: `WithinTx` was called, the repositories got the transaction's ctx (see `inTx` in
  `todo_service_test.go`), and a bad patch makes no call at all. mockery's template needs testify,
  so testify first appears here. *Why not earlier:* a ten-line fake teaches what a test double is. A
  generated mock hides that.
* **SQL migrations** (golang-migrate, embedded with `embed.FS`, run at startup) replace
  `AutoMigrate`. *Why now:* once persistence models are kept apart from the domain, the schema should
  be its own reviewed, versioned, reversible artifact, not a side effect of GORM struct tags.
  `AutoMigrate` cannot drop or rename columns and keeps no history. Mongo's equivalent is
  `database/mongo.go`, which creates the collections and the index. *Why not earlier:* for a two-table
  learning schema, `AutoMigrate` meant zero ceremony.

### Wire and the runtime DB choice

Wire resolves the graph at **compile time**, but `DB_DRIVER` is only known at **runtime**. The
solution is **one injector per storage choice** (`cmd/api/wire.go`):

```go
func initPostgresApp(ctx context.Context, cfg config.Config, log zerolog.Logger) (*gin.Engine, func(), error) {
	wire.Build(providers.PostgresSet)
	return nil, nil, nil
}
func initMongoApp(...) (*gin.Engine, func(), error) { wire.Build(providers.MongoSet); ... }
```

`config.Load` rejects an unknown `DB_DRIVER`. Then `main.go` `newRouter` switches on `cfg.DBDriver`
and calls the matching injector. The two sets in `internal/wire/providers.go` share `appSet` and
differ only in which adapter each `wire.Bind` plugs into each driven port:

```go
wire.Bind(new(ports.TodoRepository), new(*pgadapter.TodoRepository)),
```

I picked this over a single provider that switches on the driver and returns the port interfaces. A
switch like that would hide the binding in hand-written code. With two injectors, Wire still checks
every edge of both graphs.

## Pros / cons / when to use this in real life

**Pros**
* The core has no idea Gin, GORM or Mongo exist. Swapping or adding an adapter (gRPC, a queue
  consumer, another database) touches no domain or service code.
* Feature slices scale: each feature folder is self-contained and easy to find, review and delete.
* Explicit driving/driven ports make the test strategy obvious. Mock the driving port to test
  adapters. Mock the driven ports to test the service. Run one contract suite to test the driven
  adapters for real.
* Wire, generated mocks and migrations take boilerplate off your hands and fail early (generate time
  or compile time).

**Cons**
* More packages, interfaces and mapping code than the app's size needs (models and DTOs mirror the
  domain three times).
* Three generators add steps. You must rerun `wire` and `mockery` after changing constructors or
  ports, and keep the generated files committed.
* Mock-based tests can couple to call order and arguments. Keep them focused on behavior that matters,
  like transactions and activities.

**When to use it:** services you expect to live for years, with more than one way in (HTTP plus
workers, gRPC or a CLI) or more than one way out, maintained by a team. For a small CRUD tool, level 3
or 4 is enough.

```sh
export PATH=$HOME/.local/go/bin:$HOME/go/bin:$PATH
# from repo root, once: docker compose up -d

task run:pg                      # DB_DRIVER=postgres go run ./cmd/api  (migrates at startup), :8086

GIN_MODE=release task run:pg     # same, without Gin's debug lines

task test                        # go test ./...                    unit + arch tests, no Docker
task test:integration            # go test -tags=integration ./...  testcontainers: contract suite + e2e
task lint                        # gofmt -l, go vet (with and without the integration tag)

task wire:generate               # go tool wire ./cmd/api
task mock:generate               # go tool mockery
task migrate:up                  # optional: golang-migrate CLI against todo_l06
task migrate:down                # optional: roll back the last migration

# smoke test (app running on :8086, from repo root)
python3 scripts/smoke.py http://localhost:8086
```
