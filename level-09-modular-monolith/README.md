# Level 9: a modular monolith

## What this level teaches

Still one binary and one deploy, but the app is now split into **modules with hard boundaries**.
The **todo module** is level 8's feature, unchanged inside (aggregate, CQRS, outbox). It owns
`/todos`. The **activity module** owns the audit log and `GET /todos/:id/activities`. It learns
about todos **only** from the **integration events** the todo module publishes on an in-process
**event bus**. Each module owns its data (its own Postgres schema) and its own transactions. No
transaction crosses a module boundary, so activities become **eventually consistent** with todos.
That last point is the core lesson: one shared transaction gives way to per-module transactions
that stay in step through events.

```
                       one process: cmd/api, one router, one eventbus.Bus
 +------------------------- todo module ---------------------------+  +---- activity module ----+
 |  POST/PATCH/DELETE /todos/...      GET /todos, /todos/:id        |  | GET /todos/:id/activities|
 |        |                                 ^                       |  |          ^               |
 |  command.Service                   query.Service                 |  |  Service.ListActivities  |
 |        |                                 |                       |  |          |               |
 |  TodoRepository.Save: tx 1         todo.todo_views               |  |  activity.activities     |
 |    todo.todos + todo.outbox              ^                       |  |          ^               |
 |        |                                 | tx 2                  |  |          | tx 3          |
 |        |                          projection.Projector           |  |  Service.Record          |
 +--------|---------------------------------^-----------------------+  +----------^---------------+
          |                                 |                                     |
          v                                 +---------------+---------------------+
   outbox.Relay (platform, goroutine)                       |  subscribers, called in order
     1. poll todo.outbox (oldest first)             eventbus.Bus.Publish(contracts.TodoRenamed)
     2. integration.Publisher.Handle  ----------------------+
          codec.Decode -> domain event -> toContract -> contract event
     3. every subscriber committed? then mark the row processed (no transaction)
```

### Vocabulary

The domain and CQRS words are unchanged from levels 7 and 8. The modular monolith adds these:

| Term | Meaning | In code |
|---|---|---|
| **Module** | a slice of the app with its own model, data and API, behind a small public surface | `internal/modules/todo`, `internal/modules/activity` |
| **Public surface** | the only packages of a module others may import | `module.go` (package `todo`/`activity`), `todo/contracts` |
| **Integration event** | a published fact, a stable contract between modules | `contracts.TodoRenamed` |
| **Domain event** | a fact inside one module's model, private to it | `domain.TodoRenamed` (unchanged) |
| **Event bus** | delivers each published event to the handlers subscribed to its name | `eventbus.Bus` |
| **Subscriber** | a module's handler for an event; owns its transaction; idempotent | `Projector.Handle`, `Service.Record` |
| **Platform** | technical code shared by all modules, owned by none | `internal/platform/...` |

### Who owns which data

| Postgres table / Mongo collection | owner | key | written by |
|---|---|---|---|
| `todo.todos` | todo | todo id | `TodoRepository.Save` (tx 1) |
| `todo.outbox` | todo | event id | `Save` inserts (tx 1); the relay sets `processed_at` |
| `todo.todo_views` | todo | todo id | the todo `Projector` (tx 2) |
| `activity.activities` | activity | event id | the activity `Service.Record` (tx 3) |
| `public.todo_schema_migrations` | todo | | golang-migrate, for the todo migrations |
| `public.activity_schema_migrations` | activity | | golang-migrate, for the activity migrations |

In Postgres, `todo` and `activity` are **schemas**: one database, one connection pool, but every
table is qualified with its owner's name, and each module's migration creates its schema. Mongo
has no schemas, so the module's name is a **prefix**, `todo.todos`, with the same dot as the
Postgres name (Mongo's own convention for grouped collections, like GridFS's `fs.files`). That is
one rule for both databases: the first word says who owns it. Mongo indexes are as in level 8:
`todo.outbox {processed_at, _id}` and `activity.activities {todo_id}`.

Each module has its **own migrations** (`internal/modules/<m>/internal/migrations`) and its **own
golang-migrate history table**, so both can be at "version 1" and evolve without coordinating.
`platform/database.OpenPostgres(ctx, dsn, todo.PostgresMigrations(), activity.PostgresMigrations())`
runs them one module at a time. The history tables are pinned to `public` on purpose: the
default is `CURRENT_SCHEMA()`, which follows `search_path = "$user", public`. With the database
user called `todo`, `"$user"` would select the todo module's schema as soon as it exists, and the
activity history would land in the todo schema. In Mongo, each module's `PrepareMongo` creates its
own collections and indexes.

## The module rules

1. **Imports.** A module's insides live under its `internal/`, so the Go compiler rejects an import
   of `modules/todo/internal/...` from anywhere outside `modules/todo`. That leaves two public
   packages per module, and `arch_test.go` (`TestModuleBoundaries`) narrows them further:
   * `activity` may import **only** `modules/todo/contracts` from the todo module (not even its
     `module.go`);
   * `todo` imports **nothing** from `activity`. A publisher does not know who listens;
   * `platform` imports **no** module;
   * `contracts` imports only the standard library, so depending on it costs nothing.
   Only `internal/wire` (the composition root) sees every module's `module.go`.
2. **Data.** A module reads and writes only its own schema or collections. No foreign keys, joins
   or queries across modules. The activity module never looks at `todo.todos`. If it needs to
   know something about todos, it hears it in an event (or the contract gets a new field).
3. **Transactions.** A transaction never spans two modules. Each module's adapters keep their
   transaction in ctx under their own unexported `txKey`, so one module's adapters cannot even see
   another's transaction. Between modules there are only events, delivered at least once to
   idempotent subscribers.

The rules allow each module its own inner architecture. The todo module is DDD + CQRS, because
it has rules to protect. The activity module is one small `application` package plus adapters,
because it only appends and lists. A little code repeats across modules (`writeError`, the error
DTO, parsing a UUID, `TxManager`, `conn`). That repetition is on purpose: modules share the
platform, not each other's code.

## Request flow: `PATCH /todos/:id`

**The command** (synchronous, inside the request, all in the todo module, as in level 8):

1. `todo/internal/adapters/http/routes.go` routes `PATCH /todos/:id` to `handler.update`, which binds
   the body and calls `h.commands.UpdateTodo` with the raw `:id`.
2. `application/command/service.go` `UpdateTodo`: value objects first, then `todos.Get`,
   `applyChanges` (`Rename` / `Complete` / `Reopen`), then `todos.Save`. Unchanged.
3. `adapters/postgres/todo_repository.go` `Save`: in **tx 1**, the versioned `UPDATE todo.todos`
   and one `todo.outbox` row per event (`codec.Encode`). A stale version is `ErrConflict` (409).
4. The handler answers 200 from the saved aggregate.

**Delivery** (asynchronous, up to one poll interval later):

5. `platform/outbox/relay.go` `Run` ticks; `PollOnce` reads the oldest unprocessed rows through the
   todo module's `Store` (`adapters/postgres/outbox.go`).
6. `process` calls the handler, the todo module's `application/integration/publisher.go`
   `Handle`: `codec.Decode` rebuilds `domain.TodoRenamed`, `toContract` translates it into
   `contracts.TodoRenamed`, and `bus.Publish` runs its subscribers, in subscription order:
   * `todo/internal/application/projection/projector.go` `Handle` opens **tx 2** with the todo
     module's `TxManager`, loads the todo view, sets the title and `updated_at`, upserts it, commits;
   * `activity/internal/application/service.go` `Record` maps the event to an `Activity`
     (`action: "renamed"`, id = event id), opens **tx 3** with the activity module's `TxManager`,
     `ActivityLog.Add`s it (insert if absent), commits.
7. Every subscriber succeeded, so `process` calls `Store.MarkProcessed`. That is a single
   statement with no transaction around it.

**The reads:** `GET /todos/:id` is the todo module's `query.Service` over `todo.todo_views`.
`GET /todos/:id/activities` is the activity module's own route
(`activity/internal/adapters/http/routes.go`) → `Service.ListActivities` → `ActivityLog.ListByTodo`.
Both routes sit in one Gin tree, so both modules must call the parameter `:id`.

## Where the transaction lives

There are now **three kinds of transaction**, and each belongs to exactly one module.

| tx | module | opened by | covers |
|---|---|---|---|
| 1 | todo | `TodoRepository.Save` (unchanged) | the todo's state + its outbox rows |
| 2 | todo | `Projector.Handle`, via the todo `TxManager` | one event's read of and write to `todo_views` |
| 3 | activity | `Service.Record`, via the activity `TxManager` | one event's activity |

The write transaction is level 8's, unchanged. What changed is delivery. Level 8 had one
transaction around the projection **and** the processed mark. Level 9 cannot have that: the
subscribers belong to different modules, and no transaction may span two.

```go
// level 8: one transaction, the handler's writes and the mark commit together
func (r *Relay) process(ctx context.Context, m Message) error {
	return r.tx.WithinTx(ctx, func(ctx context.Context) error {
		if err := r.handler.Handle(ctx, m); err != nil {
			return fmt.Errorf("handle %s event %s: %w", m.Name, m.ID, err)
		}
		return r.store.MarkProcessed(ctx, m.ID, time.Now().UTC())
	})
}

// level 9 (platform/outbox/relay.go): deliver (each subscriber commits on its own), then mark
func (r *Relay) process(ctx context.Context, m Message) error {
	if err := r.handler.Handle(ctx, m); err != nil {
		return fmt.Errorf("handle %s event %s: %w", m.Name, m.ID, err)
	}
	return r.store.MarkProcessed(ctx, m.ID, time.Now().UTC())
}
```

Each subscriber's transaction, opened through its own module's port:

```go
// todo/internal/application/projection/projector.go
func (p *Projector) Handle(ctx context.Context, event eventbus.Event) error {
	return p.tx.WithinTx(ctx, func(ctx context.Context) error {
		return p.projectTodo(ctx, event)
	})
}

// activity/internal/application/service.go
func (s *Service) Record(ctx context.Context, event eventbus.Event) error {
	activity, err := toActivity(event)
	if err != nil {
		return err
	}
	return s.tx.WithinTx(ctx, func(ctx context.Context) error {
		return s.activities.Add(ctx, activity)
	})
}
```

(The activity's single insert would be atomic on its own. The transaction marks this module's
unit of work for one event, the place where any further write for that event would join it.)

### Before and after: one transaction vs. eventual consistency between modules

```
level 7: one transaction, one module          level 9: three transactions, two modules
                                                 tx 1 (todo)     todos + outbox
tx: todos + activities                           ...later, the relay:
    either both or neither                       tx 2 (todo)     todo_views      commits on its own
    activities are never behind                  tx 3 (activity) activities      commits on its own
                                                 mark processed (no tx)
                                                 activities lag a write by one poll
```

What can go wrong now, and why it is still correct:

| failure | what is committed | what the next poll does |
|---|---|---|
| the projector fails | nothing for this event (it runs first) | delivers to both again |
| the activity subscriber fails | the todo view, not the activity | delivers to both again: the projector's repeat changes nothing, the activity is added |
| crash or failed mark after both committed | both | delivers to both again: both repeats change nothing |

That is **at-least-once delivery**, and it only works because **every subscriber is
idempotent**: the projector upserts or deletes by todo id (level 8), and the activity insert is
keyed by the event id, so the same event twice gives one activity (`ON CONFLICT (id) DO NOTHING`,
Mongo `$setOnInsert` upsert). Order still holds per subscriber. The relay reads in id order and
**stops at the first failure**, and the bus stops at the first failing subscriber, so no
subscriber sees an event before every earlier one has reached all subscribers. A repeat is
always of the newest event a subscriber has seen, which keeps "load, change, upsert" safe.

The bus itself is plain Go: a map from event name to handlers, called synchronously in the
relay's goroutine (`platform/eventbus/bus.go`). Synchronous is what makes "every subscriber
committed, now mark it" possible. When `Publish` returns nil, all of them are done.

### Integration events are not domain events

`domain.TodoRenamed` and `contracts.TodoRenamed` look the same today. They are kept apart
because they have different jobs.

* **Domain events** are part of the todo model. They change whenever the model does: a field is
  renamed, an event splits in two, a value object replaces a string. Only the todo module sees them.
* **Integration events** are a **published promise** to other modules: plain structs with explicit
  names (`todo.renamed`), carrying only what others need, and changed only on purpose. Adding a
  field is safe; renaming or removing one would break subscribers, so that would be a new event
  (`todo.renamed.v2`) published next to the old one until every subscriber has moved.

The translation lives in one function, `integration.toContract`. If the domain changes, that
function changes, and no other module does. If other modules could see domain events, every
refactoring of the todo model would also be a change to the activity module.

Note what is stored where: the outbox still holds **domain** events in level 8's format
(`codec`). It is the todo module's private table, so its format is private too. The translation
happens on the way out, when the relay publishes.

The todo module's own projector subscribes to the **contract** events like any other module
would. There is one path out of the module, and it proves the contract carries everything a read
model needs. It could read its own domain events instead; that would be a second delivery path
to keep correct.

### Running more than one relay

As in level 8, one relay in one process needs no locks. With several instances, each relay must
first **claim** its rows (for example, `UPDATE todo.outbox SET claimed_by = $me ... WHERE id IN
(SELECT id ... FOR UPDATE SKIP LOCKED)`) and keep per-todo order with more care. Not built here,
on purpose.

**Moved without a change** (apart from import paths): the whole domain, the commands, the todo
repositories, the outbox and view adapters (bar a comment that named the relay's transaction),
the codec's logic, the relay's loop (`Run`, `PollOnce`, stop at the first failure), the todo HTTP
handlers (minus `listActivities`, which moved), the activity adapters (renamed types), logger,
server, health, and main's shutdown order.

**Changed, and why:**

* **The relay delivers, then marks.** It no longer takes a `TxManager`: no single transaction can
  cover subscribers in two modules. See *Where the transaction lives*.
* **The outbox split in two.** The generic part (`Message`, `Relay`, `Store`, `Handler`) moved to
  `platform/outbox`, so any module that publishes can use it. The todo-specific part, the codec,
  stays in the todo module as `codec.Encode/Decode`. `Message.TodoID` became `AggregateID`: the
  platform knows no todos. The table column is still `todo_id`, since the table belongs to the
  todo module.
* **The projector listens to the bus.** It takes contract events instead of outbox messages,
  writes only the todo view, and opens its own transaction (its `TxManager` port moved from
  `outbox` to `projection`, its only user). The activity half of level 8's projector moved to the
  activity module as `Service.Record`.
* **The activity log moved to its own module,** with level 7's names back: `Activity` and
  `ActivityLog` (level 8 called them `ActivityView(s)`, because they were one of two read models
  inside the todo module; now they are the activity module's own data). `ListActivities`,
  `ListByTodo`, `Add` and `writeError` keep their names.
* **Per-module storage:** schemas `todo` and `activity`, Mongo prefixes, migrations and history
  tables per module (see *Who owns which data*).
* **Wire composes modules, not adapters.** Wire writes the wiring into `cmd/api`, which may not
  import a module's `internal/` packages, so Wire can only use what a module exports:
  `todo.NewPostgres`, `activity.NewMongo`, and so on. Inside, each module wires itself in one small
  function, `newModule`, shared by both databases. The constructors also subscribe the module's
  handler on the bus. Still one injector per storage choice, still an `App{Router, Relay}`.
* **The arch test** keeps level 8's rules (with new paths), adds the projector's and publisher's
  allowed imports, and adds `TestModuleBoundaries` for what the compiler cannot check.

## Path to microservices

The boundaries this level enforces are the ones a split needs. That is why the code barely
changes when you split it:

| in the monolith | as services | what changes in code |
|---|---|---|
| `eventbus.Bus` (in process) | a broker: Kafka, NATS, RabbitMQ | `Publisher.Handle` sends to a topic (keyed by todo id, to keep per-todo order) instead of `bus.Publish`; subscribers become consumers |
| schemas `todo`, `activity` | one database per service | the DSN. Adapters never cross schemas, migrations and history tables are already per module |
| `contracts` package | a published schema (JSON Schema, Protobuf, AsyncAPI) | Go structs generated from it, versioned the same way |
| `module.go` + Wire | each service's `main` | the composition root splits; `newModule` is reused as is |
| one router | an API gateway routing `/todos/:id/activities` to the activity service | config, not code |

What does not change: the domain, the commands, the queries, the outbox, the idempotent
subscribers, at-least-once delivery. The activity module already expects to be told about todos
late, twice, or after a crash. What does change is operations: network failures, retries and
timeouts at the broker, separate deploys and versions, tracing across services, and lag to
monitor. Split when you need what services give (independent deploys and scaling, team autonomy,
fault isolation), not before. Splitting a modular monolith is cheap. Untangling a big ball of mud
is not.

## Pros / cons / when to use this in real life

**Pros**
* **Boundaries are enforced, not hoped for.** The compiler and one test stop a module from
  reaching into another. In a big codebase, that is what keeps the modules from merging back into one.
* **Each module can be understood, owned and changed alone,** with its own model, data,
  migrations and inner architecture.
* **Still a monolith to run:** one process, one deploy, one database, in-process calls, and a
  refactoring across modules is still one commit.
* **A cheap road to services** (see above), taken only when it pays.

**Cons**
* **Eventual consistency between modules,** even in one process. Activities lag todos by a poll,
  and a reader that needs both at once must cope.
* **No cross-module transactions or joins.** A report over todos and activities needs a read
  model fed by events, not a SQL join.
* **More ceremony:** contracts, a translation, a bus, per-module migrations, idempotent
  subscribers, a little duplicated code.
* **Not real isolation at runtime.** The modules share a process, a connection pool and a
  database server: a slow query or a panic in one still hurts the other, and they scale together.
* **Contracts need discipline:** versioning, and keeping old events alive until subscribers move.

**When NOT to do this:** for this app, honestly: never. It is a todo list with an audit log.
Level 7 kept both in one transaction, with no lag, no bus and no duplication, and that was the
right design. Reach for modules when a codebase has grown several areas with their own language,
data and pace of change, especially when several teams work on it, or when you expect to split
off services later. If two parts must always change together and stay strongly consistent, they
belong in **one** module. Drawing a module boundary through them buys you eventual consistency and
nothing in return.

The tests that teach this level:
* `platform/outbox/relay_test.go`: deliver then mark, in order; stop at the first failure; **a
  failed subscriber gets the message again, and the subscriber that had succeeded receives it a
  second time without harm.**
* `platform/eventbus/bus_test.go`: subscribers of a name, in order; stop at the first error.
* the **todo contract suite** (both databases): level 8's write-side tests (round trip,
  `ErrConflict`, **rollback** when the outbox insert fails), the views, and the relay over the
  real bus. It checks that a failed projection rolls back its own transaction and succeeds on
  retry; that **a failing second subscriber does not undo the projector's commit**, and the
  redelivery changes nothing; and that an event delivered but not marked is harmless to deliver again.
* the **activity contract suite** (both databases): insert-if-absent and order; **the same event
  recorded twice gives one activity**; a failed transaction persists nothing.
* `cmd/api/e2e_integration_test.go`: create, patch and delete over HTTP, one relay poll each, and
  the activity module returns `created, renamed, completed, deleted`, still after the todo is gone.
