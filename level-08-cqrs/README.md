# Level 8: CQRS with a transactional outbox

## What this level teaches

The level 7 domain stays exactly as it was. What changes is everything around it: **CQRS**
(Command Query Responsibility Segregation) splits the application into a **command side**,
which changes todos through the aggregate, and a **query side**, which only reads **read models**
(views) shaped for the API. The two sides are joined by a **transactional outbox**: `Save` writes
the aggregate's state and its events in one transaction, and a background **relay** feeds each
event to a **projector**, which updates the views. Reads become **eventually consistent**: they
may lag a write by one poll interval (100 ms by default).

![Level 8 architecture: commands go through the aggregate and Save writes todos plus outbox rows in tx 1; the outbox relay hands each event to the projector, which updates todo_views and activity_views while the relay marks the event processed in tx 2; queries read only those views](docs/architecture.svg)

### Vocabulary

The domain's words (Todo, Rename, Complete, Event, Version, Conflict, ...) are unchanged from
level 7. CQRS adds these:

| Term | Meaning | In code |
|---|---|---|
| **Command** | a request to change something; goes through the aggregate | `ports.TodoCommands`, `command.Service` |
| **Query** | a request to read something; never touches the aggregate | `ports.TodoQueries`, `query.Service` |
| **Read model / view** | data stored in the shape a query needs, derived from events | `query.TodoView`, `query.ActivityView` |
| **Outbox** | events waiting to be delivered, stored next to the state they describe | `outbox.Message`, table/collection `outbox` |
| **Relay** | the worker that delivers outbox events and marks them processed | `outbox.Relay` |
| **Projector / projection** | turns events into read model updates | `projection.Projector` |
| **Eventual consistency** | the read side catches up with the write side after a short delay | |

Storage, in both databases:

| table / collection | side | key | written by |
|---|---|---|---|
| `todos` | write | id | `TodoRepository.Save` |
| `outbox` | between | event id (UUIDv7) | `Save` inserts, the relay sets `processed_at` |
| `todo_views` | read | todo id | the projector (upsert / delete) |
| `activity_views` | read | event id | the projector (insert if absent) |

An outbox row is one event: `id`, `todo_id`, `name`, `payload`, `occurred_at`, and `processed_at`,
which stays NULL until the relay has handled it.
The outbox `payload` is `jsonb` in Postgres and the JSON text as a string in Mongo. Nothing
queries inside it, so neither database needs to understand it. Mongo indexes: `outbox
{processed_at, _id}` for the relay's poll, `activity_views {todo_id}`. Postgres has the same two
(the outbox one is partial: `WHERE processed_at IS NULL`).

## Request flow: `PATCH /todos/:id`

**The command** (synchronous, inside the request):

1. `adapters/http/routes.go` routes `PATCH /todos/:id` to `handler.update`, which binds the body
   and calls `h.commands.UpdateTodo` (`ports.TodoCommands`) with the raw `:id`.
2. `application/command/service.go` `UpdateTodo` does exactly what level 7's `Update` did:
   value objects first (`ParseTodoID`, empty patch, `NewTitle`), then `todos.Get` loads the
   aggregate, `applyChanges` calls `Rename` / `Complete` / `Reopen`, and `todos.Save` stores it.
3. `adapters/postgres/todo_repository.go` `Save` pulls the events, serializes them with
   `outbox.Encode` (`mappers.go` `toOutboxModels`), and in **one transaction** updates the row with
   the version check and inserts one `outbox` row per event. A stale version is `ErrConflict` (409)
   and nothing is written, not even the events.
4. The handler answers 200 with `toTodoResponse(todo)`: the aggregate it just saved, not a view.
   That is why the response is up to date even though the read model is not yet.

**The projection** (asynchronous, up to one poll interval later):

5. `outbox/relay.go` `Run` ticks; `PollOnce` asks `Store.Unprocessed` (`adapters/postgres/outbox.go`)
   for the oldest unprocessed rows, in id order.
6. For each one, `process` opens **one transaction** with `TxManager.WithinTx` (`adapters/postgres/tx.go`,
   which puts the GORM tx into ctx), calls the handler, then `Store.MarkProcessed`.
7. The handler is `application/projection/projector.go` `Handle`: `outbox.Decode` turns the row
   back into a `domain.TodoRenamed`, `update` loads the todo view, sets the title and `updated_at`,
   and `TodoViews.Upsert`s it; then `ActivityViews.Add` inserts the `renamed` activity. Both adapters
   use `conn(ctx)`, so they join the relay's transaction.
8. A later `GET /todos/:id` goes to `h.queries.GetTodo` → `query.Service` → `TodoViews.Get`, and
   sees the new title. `writeError` maps both `domain.ErrNotFound` and `query.ErrNotFound` to 404.

## Where the transaction lives

There are now **two kinds of transaction**, one per arrow into a store.

**1. The write transaction: aggregate state + outbox**, inside the repository's `Save`, exactly
where level 7 put it (`adapters/postgres/todo_repository.go`). Only the second insert changed:

```go
messages, err := toOutboxModels(events) // outbox.Encode for each event
if err != nil {
	return err
}
return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := saveState(tx, todo); err != nil {
		return err // ErrConflict included: rolls back
	}
	if err := tx.Create(&messages).Error; err != nil {
		return fmt.Errorf("insert outbox: %w", err) // rolls back the state too
	}
	return nil
})
```

**2. The projection transaction: read models + processed mark**, one per event, in the relay
(`outbox/relay.go`):

```go
func (r *Relay) process(ctx context.Context, m Message) error {
	return r.tx.WithinTx(ctx, func(ctx context.Context) error {
		if err := r.handler.Handle(ctx, m); err != nil {
			return fmt.Errorf("handle %s event %s: %w", m.Name, m.ID, err)
		}
		return r.store.MarkProcessed(ctx, m.ID, time.Now().UTC())
	})
}
```

Why two, and why they look different: the write transaction covers one aggregate, so the
repository that stores the aggregate owns it (level 7's rule). The projection transaction spans
three stores the relay does not own (two views and the outbox), so it comes from a `TxManager`
that hands the tx to the adapters through ctx. That is level 6's pattern, back for the one place
it fits. In Mongo, `WithinTx` is `session.WithTransaction`, and the ctx it passes carries the
session, so the views and the outbox join it with no extra code.

### Why an outbox: the dual-write problem

The obvious way to "save, then tell the world" is a **dual write**: commit the todo, then publish
the event to a message bus (or write the read model). Two systems, no shared transaction, so some
crash or network error will always land between the two writes:

* commit succeeds, publish fails (or the process dies): the event is **lost**, and the read model
  never shows the change;
* publish first, then the commit fails (a version conflict, say): the world hears about a change
  that **never happened**.

No retry order fixes this. The outbox does, by turning two writes into one: the event becomes a
row in the **same database** as the state, written in the **same transaction**. Either both exist
or neither does. Delivery then happens later, from the outbox, and can be retried until it works.
The contract suite proves the first half: when the outbox insert fails, the todo is not saved.

### At-least-once delivery and idempotent projections

The relay may hand an event over more than once: a poll can apply an event and then fail, or (once
the views live in another database, or a broker sits in between) apply it and crash before the
mark is stored. So the projector is written to be **idempotent**: applying an event twice leaves
the views exactly as applying it once.

| write | Postgres | Mongo |
|---|---|---|
| todo view, created / renamed / completed / reopened | `INSERT ... ON CONFLICT (id) DO UPDATE` (GORM `OnConflict{UpdateAll: true}`) | `ReplaceOne` with `upsert: true` |
| todo view, deleted | `DELETE ... WHERE id = ?` (0 rows is fine) | `DeleteOne` (0 matches is fine) |
| activity | `INSERT ... ON CONFLICT (id) DO NOTHING`, id = event id | `UpdateOne({_id}, {$setOnInsert: doc}, upsert)`: writes nothing if `_id` exists |

Mongo's activity insert is an upsert, not `InsertOne` + "ignore duplicate key": inside a
transaction, a duplicate-key error aborts the whole transaction.

Updates are "load the view, change one field, upsert it", which is only correct if events of one
todo are applied **in order**. Three things guarantee that: the relay reads in id order (UUIDv7,
time-ordered); it **stops at the first failure** instead of skipping ahead, so a failed event is
retried before anything after it; and a todo's events commit in id order: a save only passes the
version check if it loaded the todo after the previous save committed, so its events, recorded
after that load, get larger ids.

In this level the projection and the mark share one transaction in one database, so a crash cannot
leave an event applied-but-unmarked. Idempotency is still the rule, because it is what lets the
design grow: move the views to another database, put a broker between relay and projector, or
split the transaction (level 9 does), and the handlers stay correct. The contract suite simulates
the crash: it applies events without marking them, runs the relay, and checks that nothing doubled.

### Running more than one relay

This level runs one relay in one process, so a plain `SELECT ... WHERE processed_at IS NULL` is
safe. With several app instances, each would run a relay and they would process the same rows. The
usual Postgres fix is to select **inside** the per-event transaction with
`FOR UPDATE SKIP LOCKED`: each relay locks the rows it takes, and the others skip them. Keeping
per-todo order then needs more care (lock by todo, or partition todos across relays). Not built
here, on purpose.

* **Reads moved off the aggregate.** Level 7's README predicted it: `List` on the repository was a
  query wearing a repository's clothes. Now `domain.TodoRepository` has only what commands need
  (`Get`, `Save`), and every GET reads a view that was built for it. `domain.Activity` went the same
  way: the audit log is a read model now, `query.ActivityView`. These are the only domain changes,
  and both are deletions of what CQRS made unused (plus comments that said "activities").
* **The query side does not know the domain.** `application/query` imports only the standard
  library and uuid (the arch test enforces it). It cannot load an aggregate even by mistake, and
  the views can change shape without touching the model. The price is two small copies: it parses
  ids itself (`parseID`, the one rule of `ParseTodoID`) and has its own `ErrNotFound`. A malformed
  id on a query is simply `ErrNotFound`; the HTTP answer is the same 404 as before.
* **Commands return the aggregate's state.** Pure CQRS says a command returns nothing. Here POST
  and PATCH must keep answering with the todo (the API is fixed), and asking the read model would
  return stale data (it has not been projected yet). So a command returns the aggregate it just
  saved: it is the newest truth, and the response costs no extra read. The price is that the HTTP
  adapter has two mappers to the same JSON, `toTodoResponse` (aggregate) and
  `toTodoResponseFromView` (view).
* **`Save` writes the outbox instead of activities.** Same transaction, same rollback, same version
  check; the second insert targets `outbox`, and the rows are serialized events, not views.
* **Events are serialized by hand.** `outbox/codec.go` maps each event type to its name and a small
  JSON payload (`{"title":...}` or `{}`), and back. A `switch`, not reflection: the stored format is
  a contract with the read side (and, in a real system, with other services), so changing it must
  be a deliberate edit, not a side effect of renaming a Go field.
* **Names.** CQRS names operations by intent, and both ports now live next to each other, so
  `Create` became `CreateTodo`, `Get` became `GetTodo`, and so on. `application.TodoService` split
  into `command.Service` and `query.Service`; the package name says which side. `ActivityLog`
  became `ActivityViews`, because it is now one of two views. Kept: `UpdateTodoInput`,
  `applyChanges`, `nowUTC`, `ListActivities`, `ListByTodo`, `writeError`, `parsePage`, `WithinTx`
  and `conn` (from level 6), the sentinel errors.
* **Wire builds an `App`**, the router plus the relay, because main now runs both. Still one
  injector per storage choice.
* **main stops the relay last.** On SIGTERM the server drains its requests first, so their events
  still get projected; then main cancels the relay's own ctx and waits for it before the database
  closes. Whatever is left in the outbox is projected on the next start: that is the outbox doing
  its job.

## Eventual consistency: what a user sees

After `POST /todos` answers 201, a `GET /todos/<id>` sent at once can return **404**, and
`GET /todos` may not list the new todo yet. After a PATCH, a GET can show the old title. After a
DELETE, a GET can still find the todo. Each gap lasts until the next relay poll (100 ms by
default, plus the time to project). The smoke test polls its reads for that reason, and passes
unchanged. Writes are never stale: commands read the write model, so a PATCH right after a POST
works, and a conflict is still caught by the version.

When that is fine: lists, dashboards, search, audit logs, anything where "a moment ago" is good
enough, which is most reads. When it is not: a user who must see their own write at once
("read your writes"). The usual fixes are the one this level uses (return the new state from the
command), letting the client keep what it just wrote, or reading that one item from the write
model. If every read must be current, CQRS with async projections is the wrong tool.

## Pros / cons / when to use this in real life

**Pros**
* Each side is modeled for its job. The aggregate protects rules and knows nothing about pages
  or sorting; a view is a flat row that answers one query with one cheap read.
* **Reads scale on their own.** Most systems read far more than they write. Read models can live
  in another database, on replicas, in a cache or a search index, and be scaled, tuned or
  rebuilt without touching the write side.
* **Many projections from one stream.** A new screen, report or search index is one more projector
  over the same events. The outbox keeps processed events, so a new or broken view can be rebuilt
  by replaying them (with several consumers, each tracks its own position instead of sharing one
  `processed_at`).
* **Feeding other systems is free.** The relay can publish the same outbox to Kafka, a webhook or
  another service, with the same at-least-once guarantee and no dual write.
* The outbox makes "save and notify" reliable, which is useful even without CQRS.

**Cons**
* More moving parts for the same API: two ports, two services, a codec, a relay, a projector,
  four tables, and a background goroutine to start and stop.
* Eventual consistency is visible to users and to tests (see above); the e2e test must run a relay
  poll before it can read.
* The relay is now something to operate: a "poison" event that always fails blocks the queue
  behind it (a real system adds a retry limit and a dead-letter table and an alert), the outbox grows
  forever unless processed rows are deleted after a while, and lag should be monitored.
* Idempotency and ordering are your job, in every projector.

**When NOT to use CQRS:** here, honestly, it is overkill. One table answered every query in
level 7, the reads look exactly like the writes, and the load is tiny. Reach for CQRS when the
read side really differs from the write side: reads that dwarf writes and must scale separately,
queries that need data shaped very differently from the aggregate (joins across aggregates,
search, reports), several consumers that must react to the same changes, or a need to feed other
systems reliably. The outbox alone is worth it far earlier: as soon as a write must also
notify something outside its database. Note what this level is not: it is not event sourcing.
The `todos` table is still the source of truth; events are delivered, then kept only as history.

The contract suite (`adapters/contract_integration_test.go`) runs on both databases and covers:
the write side (`Save` writes state plus outbox rows in order; a stale save is `ErrConflict` and
writes no outbox row; **rollback**: the database is told to reject one todo's outbox rows, so
`Save` fails after writing the state, and the state is gone too), the read models (upsert twice,

(mark processed; projects in id order and skips processed events; a failing projection rolls its
view writes back and leaves the event unprocessed; **crash safety**: an event applied but not
marked is applied again with no duplicate activity).
