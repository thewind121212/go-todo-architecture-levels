# Level 7: DDD tactical patterns inside the hexagon

## What this level teaches

The hexagon from level 6 stays. What changes is the middle of it: the domain is now modeled with
the tactical patterns of Domain-Driven Design. `Todo` is an **aggregate root** with private state
and behavior methods. `TodoID` and `Title` are **value objects**: once you hold one, it is valid.
Every real change records a **domain event**, and the activity log is just those events, stored.
The **repository** saves an aggregate's state and its events in one transaction, because
**the aggregate is the consistency boundary, so it is also the transaction boundary**. Optimistic
locking with a `version` replaces `SELECT … FOR UPDATE`.

![Level 7 architecture: the application service calls behavior on the Todo aggregate, then domain.TodoRepository.Save writes its state to todos and its recorded events to activities in one transaction, through the Postgres or the Mongo adapter, and a stale version fails the whole save with 409](docs/architecture.svg)

### Ubiquitous language

The words below mean exactly one thing, in conversation and in code.

| Term | Meaning | In code |
|---|---|---|
| **Todo** | something to do; the aggregate root | `domain.Todo` |
| **TodoID** | a todo's identity, a UUID. A malformed one names no todo | `domain.TodoID`, `ParseTodoID`, `NewTodoID` |
| **Title** | what a todo says: trimmed, 1 to 200 characters | `domain.Title`, `NewTitle` |
| **Create** | start a new todo (not completed) | `domain.NewTodo` → `TodoCreated` |
| **Rename** | give a todo a different title | `todo.Rename` → `TodoRenamed` |
| **Complete** | mark a todo done | `todo.Complete` → `TodoCompleted` |
| **Reopen** | mark a done todo as not done | `todo.Reopen` → `TodoReopened` |
| **Delete** | remove a todo; its history stays | `todo.Delete` → `TodoDeleted` |
| **Event** | a fact the aggregate recorded; its name is the action (`renamed`, ...) | `domain.Event` |
| **Activity** | a recorded domain event, as the audit log shows it | `domain.Activity` |
| **Version** | how many times a todo was saved with a change; guards against lost updates. A loaded todo knows the version it was loaded at (0 = never saved) | `todo.Version()` |
| **Conflict** | someone else saved the todo after you loaded it | `domain.ErrConflict` → 409 |

A PATCH is HTTP vocabulary, not domain vocabulary. The application translates it:
`title` → **Rename**, `completed: true` → **Complete**, `completed: false` → **Reopen**.

## Request flow: `PATCH /todos/:id`

1. **Startup**: `cmd/api/main.go` `newRouter` sees `DB_DRIVER=postgres` and calls `initPostgresApp`
   in `wire_gen.go`, which builds the repository, the activity log, the application service and the router.
2. `internal/todo/adapters/http/routes.go` routes `PATCH /todos/:id` to `handler.update`.
3. `adapters/http/handlers.go` `update` binds the body into `updateTodoRequest` (`dto.go`) and calls
   `h.svc.Update` with a `ports.UpdateTodoInput`. The `:id` is passed on **raw**: the HTTP adapter no
   longer parses ids.
4. `internal/todo/application/todo_service.go` `Update` first builds value objects from the raw input:
   `domain.ParseTodoID` (malformed → `ErrInvalidID`), then the empty-patch check (`ErrEmptyPatch`), then
   `domain.NewTitle` (`ErrInvalidTitle`). Nothing has touched the database yet, so a bad patch on an
   unknown id is still 400, not 404.
5. `s.todos.Get` loads the aggregate. `adapters/postgres/todo_repository.go` reads the row and
   `mappers.go` rebuilds it with `domain.RehydrateTodo` (times converted to UTC), at its stored version.
6. `applyChanges` calls the aggregate's behavior in `domain/todo.go`: `Rename(title, now)`, then
   `Complete(now)` or `Reopen(now)`. Each method changes state and records an event **only if
   something really changed**. None of them touches the version.
7. `s.todos.Save` runs `TodoRepository.Save`: it pulls the events, opens **one** transaction, writes the
   row with `version = Version()+1` `WHERE id = ? AND version = Version()`, and inserts one activity per
   event. If no row matched,
   another request saved first: `ErrConflict`, and the transaction rolls back. No events, no write.
8. Back in `handlers.go`, the handler sends `toTodoResponse` with status 200. Any error goes to
   `writeError` in `errors.go`: `ErrInvalidID` and `ErrNotFound` → 404 `todo not found`,
   `ErrConflict` → 409, validation → 400, anything else → 500.

## Where the transaction lives

In the **repository's `Save`**, around exactly one aggregate. The application has no transaction
code at all (`internal/todo/adapters/postgres/todo_repository.go`):

```go
func (r *TodoRepository) Save(ctx context.Context, todo *domain.Todo) error {
	events := todo.PullEvents()
	if len(events) == 0 {
		return nil // nothing changed: no write, no activity
	}
	return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		if err := saveState(tx, todo); err != nil {
			return err // ErrConflict included: rolls back
		}
		activities := toActivityModels(events)
		if err := tx.Create(&activities).Error; err != nil {
			return fmt.Errorf("insert activities: %w", err) // rolls back the state too
		}
		return nil
	})
}
```

`saveState` is the optimistic lock. `todo.Version()` is the version the todo had when it was loaded,
and the mapper writes the next one (`Version()+1`). A never-saved todo (version 0) is inserted as
version 1. Any other save may only overwrite the row it loaded:

```go
if todo.Version() == 0 {
	... tx.Create(m) // version 1
}
// Optimistic lock: only overwrite the row we loaded; if someone saved since, nothing matches.
res = tx.Model(m).Where("version = ?", todo.Version()).
	Select("title", "completed", "updated_at", "version").Updates(m)
...
if res.RowsAffected == 0 {
	return domain.ErrConflict
}
```

Save does not refresh the version in memory, so a `Todo` serves one command: load it again for the
next one (every application method does). Mongo (`adapters/mongo/todo_repository.go`) does the same
inside `session.WithTransaction`, with the filter `{_id, version: Version()}` on `ReplaceOne` /
`DeleteOne`, a document at version `Version()+1`, and `MatchedCount == 0` → `ErrConflict`. If two saves really overlap, Mongo reports a write conflict and `WithTransaction`
retries; the retry no longer matches the old version, so it ends as `ErrConflict` too.

* **Rules moved into the aggregate.** In level 6 the service asked the entity what changed
  (`Rename` returned `bool`, `SetCompleted` returned an `Action`) and then decided which activities to
  write. Now the aggregate records its own events, and the application just calls behavior.
  `SetCompleted(bool)` became `Complete` and `Reopen`, because those are the words of the domain.
  `applyChanges` keeps its name and job (map the patch onto the todo) but no longer returns actions.
* **Value objects replace validation helpers.** `ValidateTitle` became `NewTitle`. Behavior takes a
  `Title`, so `Rename` can no longer fail. Building the value objects first is how the application
  keeps §13.2 "validate before touching the database".
* **Ids are parsed in the domain.** Level 6 parsed `:id` in the HTTP adapter (`todoID`). Now the
  handler passes the raw string and `domain.ParseTodoID` decides. A malformed id is the domain error
  `ErrInvalidID`, which `writeError` maps to the same 404 as before. Any driving adapter (a CLI, gRPC)
  now gets the same rule for free.
* **`TxManager` and the write-side `ActivityRepository` are gone from the application.** The aggregate
  is the unit of consistency: its state and its events must change together. So the code that owns
  the aggregate's persistence, the repository, owns the transaction too. The application cannot forget
  to open a transaction or to write an activity, because there is nothing to forget.
* **The repository interface moved into `domain`.** In DDD a repository is part of the model: it is
  how the domain talks about "all todos". There is one per aggregate. `ActivityLog` stays a port: it
  is a read-only query for the audit log, not a way to store an aggregate.
* **`service/` → `application/`.** DDD separates the *domain* (rules) from the *application service*
  (use-case orchestration with no rules of its own). The package name now says which one it is. The
  type keeps its level 6 name, `TodoService`, behind the unchanged `ports.TodoService`.
* **`FOR UPDATE` → `version`.** Level 6 read the row with `GetForUpdate` inside the transaction and
  held a lock until commit. Now `Get` is a plain read, outside any transaction, and `Save` checks the
  version it loaded. The trade-off: no lock is held while the request works, and nothing can deadlock,
  but a loser is told so (409 `todo was changed by another request`) instead of waiting its turn.
  The client must retry. For a todo app, where two edits of one todo at the same moment are rare,
  that is the better deal.
* **Delete is a behavior, saved like any change.** `todo.Delete(now)` marks the aggregate deleted and
  records `TodoDeleted`; `Save` sees `Deleted()` and removes the row (with the version check) in the
  same transaction as the event. I picked this over a separate `Remove` method because then `Save` is
  the only write path: every change, delete included, gets the same transaction, version check and
  event handling, and the `deleted` event comes from the aggregate rather than being made up by the
  application. The cost is one read before a delete (level 6 deleted blindly by id).
* Names kept: `NewTodo`, `Rename`, `Activity`, `Action`, `ListByTodo`, `UpdateTodoInput`, `TodoService`,
  `NewTodoService`, `applyChanges`, `nowUTC`, `writeError`, `parsePage`, the sentinel errors.

## Pros / cons / when to use this in real life

**Pros**
* The rules live in one place. Every way into the app (HTTP today, a worker tomorrow) goes through
  the same aggregate methods, so "a rename to the same title is not a change" cannot be forgotten.
* Invalid states are hard to build: a `Title` is always valid, a `Todo` only changes through its
  methods, and the compiler checks both.
* Domain tests are plain and fast: no mocks, no database, just "call behavior, check state and events".
* Events make the history explicit and come with a payload (`TodoRenamed.Title`). Level 8 will publish
  the same events through an outbox without touching the domain.
* Optimistic locking scales better than row locks and works the same in Postgres and Mongo.

**Cons**
* Even more code for the same API: value objects, getters, a rehydrate constructor, event types.
* Getters and `RehydrateTodo` are boilerplate that a struct with public fields didn't need. Go also
  can't forbid the zero value `domain.Title{}`; only `NewTitle` makes real ones, by convention.
* Clients must handle 409 and retry.
* `List` on the repository is a query, not an aggregate operation. It is fine here, but with many
  different views, repositories fill up with finder methods. Level 8 (CQRS) moves reads to their own model.

**When NOT to use DDD:** for this app, honestly, it is overkill. A todo has one rule about titles and
two booleans. Level 3 or 4 does the same job with far less code. DDD pays off when the domain
itself is hard: many rules that interact, invariants that span several fields or entities (an order
whose total, discounts and stock must agree), domain experts whose words you want in the code, and a
business that keeps changing its mind. Then aggregates keep each rule in one place, value objects
stop invalid data at the edge, events let other parts of the system react without coupling, and the
ubiquitous language keeps developers and experts talking about the same thing. If your service is
mostly CRUD over tables, skip the tactical patterns and keep the simpler layers.

The contract suite (`adapters/contract_integration_test.go`) runs on both databases and includes:
**rollback** (the database is told to reject one todo's activities, so `Save` fails after writing the
state, and the state is gone too) and **conflict** (load one todo three times, save the first, and the
stale update and the stale delete both return `ErrConflict` and append nothing).
