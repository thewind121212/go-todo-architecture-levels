# Todo Levels — shared spec

One deliberately tiny Todo app, built 9 times. Each level uses a more advanced architecture.
**The app's behavior never changes, only the structure does.** Diffing level N against N+1
should show exactly one new idea.

Every level has **two storage adapters, Postgres and MongoDB, behind an interface**. The choice is made at
startup by config. Every write is **transactional** in both databases.

This file is the contract. If something here is ambiguous, pick the simplest option and note it in your report.

## 4. Domain

**Todo**

| field | type | rules |
|---|---|---|
| `id` | UUID **v7** string (`github.com/google/uuid`, `uuid.NewV7()`) | generated by the app, never by the DB |
| `title` | string | trimmed; 1–200 characters (count runes) |
| `completed` | bool | false on create |
| `created_at`, `updated_at` | time, UTC | |

**Activity** is an append-only audit log of what happened to a todo.

| field | type |
|---|---|
| `id` | UUID v7 string |
| `todo_id` | UUID string (no foreign key: activities outlive deleted todos) |
| `action` | one of `created`, `renamed`, `completed`, `reopened`, `deleted` |
| `created_at` | time, UTC |

Rules:
* Timestamps are generated by the app as `time.Now().UTC().Truncate(time.Millisecond)`. Mongo stores
  milliseconds, so truncating makes both adapters round-trip identical values (tests compare them).
* UUIDv7 is time-ordered and monotonic in-process. Therefore **todos list `ORDER BY id DESC`** (newest first)
  and **activities list `ORDER BY id ASC`** (chronological). No timestamp tie-breaking needed.
* Each real change produces exactly one activity: create → `created`; title actually changed → `renamed`;
  completed false→true → `completed`; true→false → `reopened`; delete → `deleted`.
  A PATCH that changes both title and completed writes **two** activities (`renamed` then `completed`)
  in the same transaction. A PATCH that changes nothing writes none (still 200).
* Delete is a hard delete of the todo. Its activities remain.

## 5. Transactions (the core lesson)

**Every mutating request writes the todo change AND its activity rows atomically**, in Postgres and in Mongo.
If any part fails, nothing is persisted. Reads of the current todo that a mutation depends on happen inside the same transaction.

* Postgres via GORM: `db.Transaction(...)` / `tx := db.WithContext(ctx).Begin()`.
* Mongo via driver v2: `session.WithTransaction(ctx, fn)`. Inside `fn`, use the ctx it passes you
  for every collection call (that ctx carries the session).
* *Where* the transaction lives is what changes between levels (see §9). From level 3 on, the pattern is a
  `TxManager` whose `WithinTx(ctx, fn func(ctx context.Context) error) error` puts the tx/session into the
  context, and repositories pick it up from the context. Level 9 is the exception: it deliberately splits
  the transaction (see its brief).

## 6. Storage shapes

Postgres (level 1–5: GORM `AutoMigrate`; level 6+: SQL migrations):
```sql
todos(id uuid PRIMARY KEY, title text NOT NULL, completed boolean NOT NULL DEFAULT false,
      created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL)
activities(id uuid PRIMARY KEY, todo_id uuid NOT NULL, action text NOT NULL, created_at timestamptz NOT NULL)
CREATE INDEX ON activities(todo_id);
```
Mongo: collection `todos` `{_id: "<uuid string>", title, completed, created_at, updated_at}`;
collection `activities` `{_id, todo_id, action, created_at}` + index on `todo_id`. Indexes are created at startup.
Collections are created explicitly at startup if missing. Mongo can't create collections inside a multi-document transaction on all versions, so this is the safe choice.
Levels 8/9 add their own tables/collections (outbox, read models, per-module data) and document them.

## 7. HTTP API (identical in every level; framework: Gin)

| Method & path | Success | Notes |
|---|---|---|
| `GET /health` | 200 `{"status":"ok"}` | pings the DB |
| `POST /todos` `{"title"}` | 201 todo | |
| `GET /todos?limit=&offset=` | 200 `{"items":[todo...],"limit":20,"offset":0}` | limit default 20, must be 1–100; offset default 0, must be ≥0; `items` is `[]`, never `null` |
| `GET /todos/:id` | 200 todo | |
| `PATCH /todos/:id` `{"title"?, "completed"?}` | 200 todo | body with neither field → 400 |
| `DELETE /todos/:id` | 204 | |
| `GET /todos/:id/activities` | 200 `{"items":[activity...]}` | `[]` when none; no 404 check |

JSON field names are exactly as in §4 (snake_case). Timestamps are RFC 3339 UTC.

Errors: always `{"error":"<message>"}`.
* 400: invalid JSON, validation failure, bad limit/offset, empty PATCH.
* 404: unknown id **or malformed id** (not a UUID). Message `todo not found`.
* 500: anything else. Log the real error; respond `{"error":"internal error"}`.

Map domain errors to status codes in **one place** per level (e.g. one `writeError` func).
Domain errors are sentinel values (`ErrNotFound`, `ErrInvalidTitle`, ...) checked with `errors.Is`.

## 8. Tests

* `go test ./...`: **unit tests only**. These need no Docker and must be fast: handler tests with
  `httptest`, plus business-rule tests using fakes (hand-written until level 6, mockery from level 6).
* `go test -tags=integration ./...`: **integration tests** using testcontainers-go
  (`modules/postgres`, and `modules/mongodb` with `mongodb.WithReplicaSet("rs0")`). They spin up their own
  containers and do not use the compose DBs.
* Integration tests run **one shared contract suite against BOTH adapters**, so you can see the two behave
  identically. The suite must include a **rollback test**: start a transaction, write a todo (and/or activity),
  return an error, then assert nothing was persisted. Do this for Postgres and Mongo.
* Smoke test: with compose running, start the app with each `DB_DRIVER` and run
  `python3 scripts/smoke.py http://localhost:80NN` from repo root. It must PASS for both drivers.
  Stop the app afterwards.

## 9. Progression: what each level adds (do not use a tool before its level)

| Level | Structure | Where the transaction lives | DI | Logging | Schema | Fakes/mocks | Task runner |
|---|---|---|---|---|---|---|---|
| 1 single-file | one `main.go` | inside each store method | manual in `main` | std `log` | AutoMigrate | hand fakes | none |
| 2 flat | package `main`, split files | inside each store method | manual in `main` | std `log` | AutoMigrate | hand fakes | none |
| 3 layered | handler / service / repository | **service** via `TxManager` + ctx | manual in `main` | zerolog | AutoMigrate | hand fakes | Taskfile |
| 4 by-feature | `internal/todo`, `internal/activity`, `internal/platform` | todo service via platform `TxManager` | manual in `main` | zerolog | AutoMigrate | hand fakes | Taskfile |
| 5 clean | entity / usecase / adapter / infrastructure, one use case per struct | use case interactor | manual composition root | zerolog | AutoMigrate | hand fakes | Taskfile |
| 6 hexagonal | go-scaffolding style: domain / ports / service / adapters | service via `ports.TxManager` | **Wire** | zerolog | **SQL migrations** (golang-migrate, embedded) | **mockery v3** | Taskfile |
| 7 DDD | aggregate, value objects, domain events | repository saves aggregate + its events in one tx | Wire | zerolog | SQL migrations | mockery | Taskfile |
| 8 DDD+CQRS | commands / queries / projections + outbox | write tx = aggregate + outbox; projector tx = read model + mark processed | Wire | zerolog | SQL migrations | mockery | Taskfile |
| 9 modular monolith | `modules/todo`, `modules/activity`, shared platform | per-module tx; cross-module via outbox + idempotent consumer | Wire | zerolog | SQL migrations per module | mockery | Taskfile |

From level 3 on, use `http.Server` with graceful shutdown on SIGINT/SIGTERM. Levels 1–2 may just `router.Run`.
Tools can be pinned via the `tool` directive in `go.mod` (`go get -tool ...`, run with `go tool wire`, `go tool mockery`).

## 10. Code quality bar (this is a learning template; clarity beats cleverness)

* Idiomatic, `gofmt`-clean, `go vet`-clean. Small functions, obvious names, no dead code, no TODOs.
* Add only the abstraction your level teaches. No speculative interfaces, generics, or helpers.
* Comments are sparse. Use them to explain *why*, especially at the spots that teach the level's lesson
  (where the tx starts, why an interface lives where it does). Don't narrate obvious code.
* Wrap errors with `%w` and context (`fmt.Errorf("insert todo: %w", err)`). Propagate `context.Context` everywhere.
* No global mutable state (except Gin's mode).
* Use `gin.SetMode(gin.TestMode)` in tests.
